UDP Merger Anatomy

Two redundant UDP feeds carry the same sequence-numbered messages, out of order, with duplicates. Three small classes turn that into one strictly-ordered, gap-free, zero-copy-on-the-fast-path stream. This is how, with a diagram and a full worked trace for each piece.

01

Sequencer

udp_feed_merger.cpp — class Sequencer

The merger's cursor: one number, the next sequence value it's waiting for. Everything else in the file exists to answer one question this class asks — "has that arrived yet?" — and to keep advancing it once the answer is yes.

API

SignatureContract
uint64_t getNextSeq() constThe next sequence number the downstream consumer is waiting for. Starts at 1 — feed sequence numbers are 1-based.
uint64_t incrementSeq()Advances the cursor by one and returns the new value. Called exactly once per delivered message, never per packet — duplicates and buffered arrivals don't move it.
 
class Sequencer {
    std::uint64_t next_seq_ = 1;
public:
    [[nodiscard]] std::uint64_t getNextSeq() const { return next_seq_; }
    [[nodiscard]] std::uint64_t incrementSeq() { return ++next_seq_; }
};
Why it's its own class — UdpMergeConsumer compares against it, UdpBuffer bounds-checks against it, and neither owns it. Splitting the cursor out means the ordering invariant lives in exactly one place, and it's trivial to reason about in isolation.
02

UdpBuffer

udp_feed_merger.cpp — class UdpBuffer

A fixed-capacity ring, indexed by sequence number, that holds packets which arrived ahead of the cursor until the gap in front of them closes. Its whole reason to exist: an out-of-order arrival needs somewhere to sit that isn't a per-packet heap allocation.

Layout

API

SignatureContract
UdpBuffer()Sizes and zero-fills payload_storage_ once: Capacity × MaxPayloadSize bytes. The only allocation in the object's lifetime.
AddResult addPacket(uint64_t next_expected, const PacketInput&) noexceptBounds-checks and stores an out-of-order packet. Never throws — every failure mode is a value in AddResult for the caller to act on.
template<Consumer> bool consumePacket(uint64_t seq, Consumer&&)If seq is resident, hands the callback a PacketView straight out of ring storage and frees the slot; returns whether it found anything.
struct PacketInput { char feed; uint64_t seq; const char* data; size_t len; }Bundles addPacket's four inputs so the call site passes one aggregate instead of four positional arguments.
struct PacketView { char feed; span<const char> payload; }A non-owning view into ring storage. Valid only for the duration of the consume() call — the slot is freed immediately after.
enum class AddResultstored, duplicate, out_of_window, payload_too_large, invalid_data, slot_collision.

addPacket, in order

  1. Reject a null pointer paired with a nonzero length (invalid_data), then reject a payload bigger than MaxPayloadSize (payload_too_large) — before touching the ring at all.
  2. Reject anything not strictly ahead of next_expected, and anything more than Capacity ahead of it (out_of_window). This is the line that keeps two live sequence numbers from ever landing on the same slot: they'd have to be Capacity apart, which this check refuses to let happen.
  3. Compute the slot via indexFor(seq). If it's occupied, this exact seq means duplicate (already buffered, harmless); any other seq in that slot means slot_collision — the window check above should make this unreachable, so it exists purely to fail loudly instead of corrupting a live packet.
  4. Copy the payload into payload_storage_ at that slot's offset, record seq/len/feed, mark it occupied, return stored.
if (seq <= next_expected ||
    seq - next_expected > static_cast<std::uint64_t>(Capacity)) {
  return AddResult::out_of_window;
}

UdpMergeConsumer

udp_feed_merger.cpp — class UdpMergeConsumer

Owns a Sequencer and a UdpBuffer and is the merger's only entry point. handlePacket is called once per received packet, from either feed, in whatever order they physically arrive — everything above exists to make that one function correct and fast.

Control flow

API

SignatureContract
void handlePacket(char feed, uint64_t seq, const char* data, size_t len)The merger's only entry point. Called once per packet received, regardless of which feed it came from.
The drain loop delivers from the ring, not from the triggering packet — after the fast-path deliver call, the while loop keeps asking consumePacket(next_seq_, …) and delivering whatever it finds, so one arriving packet can release an arbitrarily long run that was waiting in the ring, all inside a single handlePacket call.
deliver(feed, seq, data, len);
auto expected = sequencer_.incrementSeq();

while (buffer_.consumePacket(
    expected,
    [this, expected](const UdpBuffer::PacketView& packet) {
      deliver(packet.feed, expected, packet.payload.data(), packet.payload.size());
    })) {
  expected = sequencer_.incrementSeq();
}

Worked example

udp_feed_merger.cpp — main()

The file's own test data, traced call by call. Twelve send calls, twelve calls to handlePacket, six of them producing output — in strict order, each sequence number exactly once, regardless of which feed happened to carry the winning copy.

Actual program output

Feed: A, Seq: 1, data: Message 1 Feed: B, Seq: 2, data: Message 2 Feed: A, Seq: 3, data: Message 3 Feed: A, Seq: 4, data: Message 4 Feed: B, Seq: 5, data: Message 5 Feed: A, Seq: 6, data: Message 6

Six lines from twelve calls — the other six were absorbed silently, either as late duplicates (seq < next_seq_) or as a second copy of a packet already resident in the ring (AddResult::duplicate). Sequence numbers 1 through 6 appear exactly once each, in order, sourced from whichever feed's copy happened to be processed first.

Design Notes

Cross-cutting properties that don't belong to any one class, but shape how the merger behaves as a whole.

Zero-copy fast path

A packet that arrives exactly in order goes straight from handlePacket to deliver — no ring, no memcpy. Only a packet arriving ahead of schedule pays the copy-into-the-ring cost, and only once.

One allocation, ever

payload_storage_ is sized in UdpBuffer's constructor — Capacity × MaxPayloadSize bytes — and never resized. Steady-state operation never calls new.

Ordering guarantee

Every sequence number is delivered exactly once, strictly increasing, no gaps. A late duplicate and an already-buffered duplicate are both silently absorbed rather than re-delivered.

Failure means a broken contract

out_of_window, payload_too_large, invalid_data, and slot_collision all throw. Each means the caller violated the exercise's own guarantees — more than Capacity messages outstanding, an oversized packet — not something the merger can route around.

Single-threaded, deterministic

No locks, no background thread, no timers. Replaying the same interleaving of handlePacket calls always produces byte-identical output — the same property that makes main()'s scripted send order a complete test.
